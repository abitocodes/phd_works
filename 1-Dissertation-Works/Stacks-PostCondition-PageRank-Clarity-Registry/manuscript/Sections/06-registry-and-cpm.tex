\section{The registry and \cpm}
\label{sec:registry}

\subsection{Architecture}

Figure~\ref{fig:architecture} shows the components. An indexer fills a PostgreSQL database with contracts, transactions, post-conditions and asset events. For the history it reads a self-hosted Stacks node and Stacks Blockchain API rather than the hosted API, because a full backfill through the hosted service is slow under its rate limits and because a pinned archive makes the evaluation reproducible. New blocks arrive through Chainhooks or the node's event interface \cite{hiroapi,chainhooks2026}. An analyzer parses each contract, extracts the references and allowances of Section~\ref{sec:method}, computes the normalized hash and runs static checks. A daily job builds the graph, computes \PCER\ and the clone families, and refreshes the search index. The web front end and the \cpm\ client read from the same search API, and \cpm\ checks what it receives against the chain.

\subsection{Package model}

\textbf{Scopes.} Every contract already has a publisher: the address in its principal. The registry therefore indexes every contract under its principal, and a publisher may claim a readable scope in two ways. The address itself is always a valid scope. A BNS name such as \code{alice.btc} becomes a scope if it resolved to the deployer's address when the claim was made. BNS names are SIP-009 tokens and can be sold \cite{bnsv2}, so the registry records the name, its owner and the block height of the claim. If the name later changes hands, the scope is frozen: existing versions keep their identity, new versions need a new claim, and \cpm\ warns when a scope's owner differs from the one recorded in the project's lockfile. This guards against the takeover of a trusted name, an attack known from other registries \cite{ladisa2023sok}.

\textbf{Versions.} A deployed contract cannot change, so each version of a package is a separate contract, and \code{token-v1} and \code{token-v2} are unrelated on chain. The publisher states the relation in a manifest: the package name, the semantic version of each contract, the predecessor of each version, the matching testnet principal, a license identifier, a repository URL, a README and links to audit reports. The registry accepts a manifest only if every listed contract was deployed by the scope's address, and only if the manifest is signed by that address with a SIP-018 structured-data signature \cite{sip018} or submitted in a transaction from it. No other key infrastructure is needed, because the address that signs is the address that deployed.

\textbf{Unclaimed contracts.} Contracts without a manifest are still indexed, under their principal, with trait labels, a clone family and a score, but without versions or a README.

\subsection{Commands}

\cpm\ wraps Clarinet rather than replacing it. Table~\ref{tab:cpm} lists its commands. The central distinction is between referencing and copying. On npm, installing a package copies code into the project. A Clarity contract that a project wants to \emph{use} is already deployed, shared by everyone, and called by its principal; what a project adds is a reference. \code{cpm add} records that reference as a Clarinet requirement, so that local tests can call a copy that Clarinet deploys on its local networks \cite{clarinet}, while a mainnet deployment deploys nothing for it. A project that wants its own instance, a token built from a SIP-010 template for example, \emph{copies} the source with \code{cpm create} or \code{cpm fork} and deploys the copy under its own address. Copying is allowed only when the package's license permits it; publication on chain does not make code open source.

\subsection{Lockfile}

Version ranges, the main subject of npm lockfiles, do not exist for deployed contracts. The \cpm\ lockfile records identities instead: for each dependency, its mainnet principal and testnet counterpart, its code hash as returned by \code{contract-hash?}, its deployment height and Clarity version, its family hash, its license, the scope owner seen when it was added, and whether it was referenced or copied. \code{cpm verify} reads the code hashes from a node, through a read-only call to a contract that returns \code{contract-hash?} such as the registry contract below, and compares them with the lockfile, so that a compromised API or mirror cannot substitute different source for a contract the project depends on.

\subsection{An optional registry contract}

Names can also live on chain. A small registry contract offers \code{publish(name, version, contract)}, which checks with \code{principal-destruct?} that the address part of \code{contract} equals \code{tx-sender}, stores the result of \code{contract-hash?} for that contract next to the name and version, and prints an event for indexers. It also offers a read-only function that returns \code{contract-hash?} for any principal, which \cpm\ uses for verification. The registry works without this contract; with it, names and hashes are recorded on chain and do not depend on the operator of the web service.

\subsection{Signals shown to users}

A ranking orders results; it does not say that a contract is safe. Each contract page and \code{cpm audit} show the signals of Table~\ref{tab:signals} next to the score, and the registry keeps indexing separate from recommending. Every contract is indexed. A ``recommended'' label, if offered, requires criteria beyond the score, such as an audit link, a minimum age and no high-severity findings, and the registry does not call a contract malicious on the strength of its score.
