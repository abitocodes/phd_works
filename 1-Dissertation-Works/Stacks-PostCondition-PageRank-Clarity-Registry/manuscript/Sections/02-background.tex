\section{Background}
\label{sec:background}

\subsection{Stacks and Clarity}
\label{sec:bg-clarity}

Stacks is a blockchain for smart contracts that settles to Bitcoin \cite{ali2021stacks}. Its contracts are written in Clarity, a language without recursion or unbounded loops, so the cost of a call can be bounded before it runs \cite{sip002}. Clarity is not compiled: the node stores and interprets the source text, and the Stacks Blockchain API returns that text, together with the contract's interface (ABI), for any deployed contract \cite{hiroapi}.

A contract is identified by a contract principal of the form \code{SP\ldots ABC.amm-pool}. The address before the dot is the standard principal that deployed the contract, so the identifier itself records who published the code. A contract calls another with \code{contract-call?}. In \emph{static dispatch} the callee is written as a literal principal; in \emph{dynamic dispatch} the callee is a function argument whose type is a trait, and the caller chooses the concrete contract at run time \cite{sip002}. A trait is declared with \code{define-trait}; a contract states that it conforms to a trait with \code{impl-trait} and imports a trait for use as an argument type with \code{use-trait}. Both refer to the contract that defines the trait. Clarity~5 also accepts a constant as the target of \code{contract-call?} \cite{sip039}. Static dispatch therefore yields a call graph that can be read from the source, while dynamic dispatch leaves the callee open until a transaction supplies it.

Token standards are traits. SIP-009 defines non-fungible tokens \cite{sip009}, SIP-010 fungible tokens \cite{sip010} and SIP-013 semi-fungible tokens \cite{sip013}. The Stacks Blockchain API can list the contracts whose ABI matches a given trait \cite{hiroapi}, which lets a registry label conforming contracts without parsing them.

\subsection{How Stacks authorizes asset movement}
\label{sec:bg-authorization}

\textbf{No allowance in SIP-010.} The SIP-010 trait declares a \code{transfer} function that takes an amount, a sender, a recipient and an optional memo, together with read-only functions for the name, symbol, decimals, balance, supply and token URI \cite{sip010}. There is no function that lets one principal spend another's tokens. Typical implementations accept a transfer only when the sender is the transaction sender. In Clarity, \code{tx-sender} stays equal to the account that signed the transaction through nested contract calls, unless a contract switches the context to itself, while \code{contract-caller} is the immediate caller \cite{sip002}. A decentralized exchange called by a user can therefore move the user's tokens within that call without any prior approval. What protects the user is the post-condition mechanism.

\textbf{Post-conditions.} A Stacks transaction carries a list of post-conditions and a post-condition mode, both covered by the signature \cite{sip005}. Each post-condition names a principal (the transaction origin, a standard principal or a contract principal), an asset (STX, a fungible token or a specific non-fungible token) and a condition. For STX and fungible tokens the condition compares the amount the principal sends during the transaction with a stated amount using $=$, $>$, $\geq$, $<$ or $\leq$; for a non-fungible token it states that the principal will or will not send it. After execution the node checks every post-condition; if one fails, the transaction is aborted and its effects are rolled back, although it stays in the block and its fee is paid. The mode decides what happens to transfers that no post-condition mentions: in \emph{Allow} mode they are permitted, in \emph{Deny} mode they abort the transaction \cite{sip005}. Stacks.js builds transactions in Deny mode unless told otherwise \cite{hiropostconditions}. SIP-040, which took effect with Clarity~5 in Epoch~3.4 (Bitcoin block 943,333, April 2026), adds a third mode, \emph{Originator}, which applies Deny rules to the assets of the transaction origin and Allow rules to every other principal, and adds a \emph{may send} condition for non-fungible tokens \cite{sip040,sip039}. Its motivation is that DeFi calls move assets between contracts in ways the user cannot predict, which pushed users towards Allow mode.

\textbf{Asset allowances in contracts.} Clarity~4 (SIP-033), activated at Bitcoin block 923,222 in November 2025, lets a contract bound asset outflows while it runs code it does not control \cite{sip033}. \code{restrict-assets?} takes a principal, a list of allowances and a body; it executes the body and then checks the principal's outflows against the allowances. \code{as-contract?} switches \code{tx-sender} and \code{contract-caller} to the contract itself, executes the body, and checks the contract's own outflows. The allowance expressions are \code{with-stx}, \code{with-ft}, \code{with-nft} and \code{with-stacking}, each naming an asset and a limit; \code{with-all-assets-unsafe}, allowed only in \code{as-contract?}, lifts every limit. Clarity~6, which took effect with Epoch~4.0 at Bitcoin block 960,230 in July 2026, renames \code{with-stacking} to \code{with-staking} and adds \code{with-pox} for calls into the PoX contract; it adds no new kind of transaction post-condition \cite{sip044}. If an outflow exceeds an allowance, the body's effects are rolled back and the expression returns the index of the violated allowance as an error; if an asset with no allowance moves, it returns \code{(err u128)}. Clarity~4 removes the old \code{as-contract}, which switched context without any limit. Listing~\ref{lst:as-contract} shows the pattern. SIP-033 also adds \code{contract-hash?}, which returns the SHA-512/256 hash of a contract's code body so that one contract can check that another follows a known template, and the keyword \code{current-contract}.

\begin{lstlisting}[language=Clarity,caption={A Clarity~4 asset allowance. Only the vault's owner may trigger a payout, and while the body runs at most \code{amount} of the token may leave the vault.},label={lst:as-contract},float=htbp]
(define-constant OWNER tx-sender)
(define-public (pay-out (amount uint) (recipient principal))
  (begin
    (asserts! (is-eq contract-caller OWNER) (err u401))
    (as-contract? ((with-ft .token "tok" amount))
      (try! (contract-call? .token transfer amount current-contract recipient none)))))
\end{lstlisting}

\textbf{Standing authorizations between contracts.} Some protocols keep explicit lists of contracts they trust. In the ExecutorDAO pattern, used by several Stacks DAOs, the core contract keeps a map of enabled extensions, a governance call to \code{set-extension} enables or disables one, and an enabled extension may act in the DAO's sending context, checked through \code{contract-caller} \cite{executordao}. Such a map is the closest Stacks analogue of a standing allowance: an explicit transaction sets it, and it stays in force until changed.

\subsection{Package registries and popularity}
\label{sec:bg-registries}

Package registries index published code and rank search results with some mix of text relevance and popularity. The Go package site computes, for each module matching a query,
\begin{equation}
\label{eq:pkgsite}
\mathrm{score} = \mathrm{ts\_rank}(q,m)\cdot\bigl(\ln(e + \mathrm{imported\_by}(m))\bigr)^{\alpha}\cdot\rho_{\mathrm{redist}}(m)\cdot\rho_{\mathrm{mod}}(m),
\end{equation}
where $\mathrm{ts\_rank}$ is PostgreSQL's full-text rank, $\mathrm{imported\_by}$ counts importing packages, and the last two factors penalize modules that cannot be redistributed or lack a \code{go.mod} file \cite{pkgsite}. Because of the logarithm, doubling the number of importers raises that factor's logarithm by about $\ln 2$ instead of doubling the factor. Dependency networks of npm, Cargo, CRAN and other ecosystems have been studied as graphs \cite{kikas2017structure,decan2019empirical}, and PageRank over the npm dependency graph has been used to find packages in decline \cite{mujahid2021centrality}.

The tea protocol paid rewards according to teaRank, a score of a package's place in the dependency graph \cite{tea2022}. The incidents described in Section~\ref{sec:introduction} show what happens when such a score carries money: spam packages that depend on one another \cite{sonatype2024tea,aws2025tea}. Registries face other supply-chain attacks as well, including typosquatting and account takeover \cite{ohm2020backstabber,ladisa2023sok,vu2020typosquatting}, and a small number of maintainer accounts can reach a large share of npm through transitive dependencies \cite{zimmermann2019small}.

\subsection{PageRank, the restart distribution and Sybil attacks}
\label{sec:bg-pagerank}

Let $G=(V,E,w)$ be a directed graph with positive edge weights, and let $P$ be the matrix with $P_{uv}=w(u,v)/\sum_x w(u,x)$ for nodes with out-edges and zero rows for nodes without them. With damping $d\in(0,1)$ and a restart distribution $\boldsymbol{\pi}$ over $V$, PageRank is the fixed point of
\begin{equation}
\label{eq:pagerank}
\mathbf{r} = (1-d)\,\boldsymbol{\pi} + d\,P^{\top}\mathbf{r} + d\,\delta(\mathbf{r})\,\boldsymbol{\pi},
\qquad
\delta(\mathbf{r}) = \sum_{v:\,\text{no out-edges}} r_v ,
\end{equation}
so that the mass held by dangling nodes returns to the restart distribution \cite{page1998pagerank,langville2006google}. The original algorithm uses a uniform $\boldsymbol{\pi}$. Topic-sensitive and personalized PageRank use a non-uniform one \cite{haveliwala2003topic,jeh2003scaling}, and TrustRank concentrates it on a small set of pages judged by hand to be reputable \cite{gyongyi2004trustrank}. EigenTrust uses pre-trusted peers in the same role \cite{kamvar2003eigentrust}. AWP and EndorseRank use $d=0.85$ and a uniform restart \cite{do2023awp,kwon2026endorserank}.

A Sybil attack creates many identities controlled by one party \cite{douceur2002sybil}. Against PageRank it takes the form of a link farm, a set of pages that exist to link to a target; alliances of farms raise the scores of all participants \cite{gyongyi2005alliances}. Cheng and Friedman showed that a reputation function that is symmetric in node identities cannot be Sybil-proof, and that asymmetric, flow-based functions computed from a trusted source can be \cite{cheng2005sybilproof}. Social-graph defenses such as SybilGuard and SybilRank rest on the same observation: an attacker can create nodes and edges among them freely, but the number of \emph{attack edges} from honest nodes into the attacker's region is limited, and a walk that starts at honest nodes rarely crosses them \cite{yu2006sybilguard,cao2012sybilrank}. Analyses of PageRank on communities make the dependence on inbound links precise \cite{bianchini2005inside}, and Robust PageRank limits how much of a node's score can come from any small set of contributors \cite{andersen2008robust}. Section~\ref{sec:method} applies these ideas to contracts.
